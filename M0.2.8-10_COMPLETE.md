## M0.2.8: Fixture Test Runner ✅

**Purpose:** Eliminate manual testing via declarative YAML fixtures

### What It Does

- Load test fixtures from YAML files
- Execute middleware against test inputs
- Verify outputs, errors, routing, message drops
- Generate pass/fail reports

### Configuration

```yaml
# test/fixtures/route-filter.yaml
fixtures:
  - name: "premium-tier routes correctly"
    input: { tier: "premium", amount: 1000 }
    expected_output: { name: "Alice", total: 1100 }
    expected_route: "premium-processing"

  - name: "negative amounts are dropped"
    input: { amount: -50 }
    expected_dropped: true

  - name: "missing email triggers error"
    input: { name: "Bob" }
    expected_error: true
```

### CLI Usage

```bash
# Build
go build -o bin/midctl ./cmd/midctl

# Run all fixtures from directory
./bin/midctl test test/fixtures/ --config examples/config.yaml
# Output: "38 fixtures passed, 0 failed, 0 errors"

# Run single fixture file
./bin/midctl test test/fixtures/route-filter.yaml --config examples/config.yaml
```

## M0.2.9: Message Ordering Guarantees ✅

**Purpose:** Preserve message order for ordered sources (databases, ordered queues)

### What It Does

- Optional per-route `ordering: required` mode
- Ordered routes: serialized processing (1 worker = FIFO)
- Unordered routes: parallel processing (default 4 workers)
- No performance penalty for unordered messages

### Configuration

```yaml
routes:
  event-replay:
    from: ordered-source
    ordering: required  # ← Serial FIFO processing
    steps:
      - filter: { expr: "status != 'cancelled'" }

  standard-processing:
    from: http-source
    # ordering omitted → parallel (4 workers)
    steps:
      - translate: { expr: "{name: name, total: amount}" }
```

### Implementation

**Files Created:**
- `internal/ordering/ordering.go` — Ordering helper functions
- `internal/ordering/ordering_test.go` — 18 comprehensive tests
- `examples/ordered-route.yaml` — Single ordered route
- `examples/mixed-ordering.yaml` — Mixed ordered/unordered routes

**Modified Files:**
- `internal/config/schema.go` — Added `Ordering` field to RouteSpec
- `internal/factory/pipeline.go` — Ordering detection + worker constraint

### Features

✅ **Smart Worker Pooling:**
- `ordering: required` → 1 worker (preserves order)
- `ordering: none` → N workers (parallel, default)
- Omitted → defaults to unordered (Phase 1 compatible)

✅ **Elegant Integration:**
- Leverages existing `NewExecutorWithWorkers()` infrastructure
- No executor changes needed
- Single-line ordering detection in pipeline factory

✅ **Quality:**
- 18 tests (all with `-race` flag)

## M0.2.10: Observability (Metrics & Tracing) ✅

**Purpose:** Production monitoring with Prometheus + OpenTelemetry

### What It Does

- **Prometheus Metrics:** Per-route counts, latencies, retries, errors
- **OpenTelemetry Tracing:** Distributed trace context, span nesting
- **Multiple Exporters:** stdout (dev), Jaeger (ops), Datadog (cloud)
- **Configurable Sampling:** Reduce overhead on high-volume flows

### Metrics Exposed

```prometheus
# Prometheus format (localhost:2112/metrics)

# Counters
dim_messages_total{route="premium-processing",status="success"} 1500
dim_messages_failed{route="premium-processing"} 5
dim_retries_total{route="premium-processing"} 32
dim_dead_letters_total{route="premium-processing"} 3

# Gauges
dim_workers_in_flight{route="premium-processing"} 3

# Histograms (latency percentiles)
dim_message_latency_ms{route="premium-processing",quantile="0.50"} 5
dim_message_latency_ms{route="premium-processing",quantile="0.90"} 18
dim_message_latency_ms{route="premium-processing",quantile="0.99"} 45
```

### OpenTelemetry Spans

```
span: message_processing (route=premium-processing)
  ├─ span: step_execution (step=authorize)
  │   └─ duration: 1ms
  ├─ span: step_execution (step=filter)
  │   └─ duration: 2ms
  ├─ span: step_execution (step=translate)
  │   └─ duration: 3ms
  └─ span: output_write
      └─ duration: 1ms
```

### Configuration

```yaml
version: 1

observability:
  metrics:
    enabled: true
    prometheus_addr: ":2112"
  
  tracing:
    enabled: true
    otel_exporter: "stdout"  # or "jaeger", "datadog"
    sample_rate: 0.1  # 10% sampling (reduce overhead)
    jaeger_endpoint: "http://localhost:14268/api/traces"  # if jaeger
```

## Architecture Integration

### Updated Pipeline

```
HTTP Request
    ↓
HTTP Source Adapter
    ├─ Route detection (header/query/path)
    └─ Correlation ID + observability init
    ↓
Message Router (multi-route)
    ↓
Order Detection (M0.2.9)
    ├─ ordered: required → 1 worker
    └─ ordered: none/omitted → 4 workers
    ↓
Worker Pool Executor (M0.2.1)
    ├─ Concurrent processing
    └─ Metrics recording (M0.2.10)
    ↓
Step Pipeline:
    ├─ Authorize, Filter, Translate, Route, Wiretap, Idempotent
    ├─ Tracing (M0.2.10) - per-step spans
    └─ Metrics (M0.2.10) - latency histograms
    ↓
Retry Loop (M0.2.2)
    ├─ Transient error → backoff
    └─ Metrics (M0.2.10) - retry counter
    ↓
Output:
    ├─ Success → File Sink + Metrics
    └─ Error → Dead-Letter + Metrics
    ↓
Observability Export (M0.2.10)
    ├─ Prometheus: `:2112/metrics`
    └─ OpenTelemetry: stdout/jaeger/datadog
    ↓
Test Fixtures (M0.2.8)
    └─ YAML-driven integration testing
```

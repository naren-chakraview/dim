## Design Decisions

### JSONata over CEL
**Why:** Widely used in integration middleware (Ballerina, Apache Camel), better JSON/object manipulation, xpath-like navigation for nested structures.

### Blues/jsonata-go v1.5.4
**Why:** Pure Go implementation, no external dependencies, 9/10 spec compliance for Phase 0 needs.

### Message Envelope Pattern
**Why:** Decouples application data (body) from transport metadata (headers, correlation ID, route info, principal), enabling tracing and lineage tracking.

### Bounded Channels
**Why:** Prevents unbounded memory growth, enables backpressure awareness without explicit flow control.

### Step Interface
**Why:** Composable, pluggable steps; enables filter→translate chains and future step types (route, wiretap, idempotent, authorize).

### Single-Worker Executor (Phase 0)
**Why:** Simplifies implementation, enables in-order message processing. Multi-worker pools and fairness algorithms deferred to M0.2+.

### JSONL Output Format
**Why:** Streaming-friendly, one JSON object per line, parseable incrementally without loading entire file into memory.

### DeadLetterEnvelope
**Why:** Preserves failed message context (original body, error reason, failed step index) for debugging and recovery workflows.

| Latency | ~1-5ms per message | JSONata compilation cached, no retry loops |
| Memory | Bounded by channel buffer | Default 100-message buffer per channel |
| Concurrency | Single-threaded | In-order processing guaranteed |
| Reliability | Basic error routing | Retry logic deferred to M0.2 |

3. **Fixture tests:** YAML test cases validated against step implementations

## Known Limitations (Phase 0)

- Single-threaded: one message at a time
- No retry logic (M0.2)
- No multi-route support (M0.2)
- No route, wiretap, idempotent, authorize steps (M0.2)
- HTTPSource hardcoded to port 8080, path /ingest (configurable in M0.2)
- FileSink creates files in ./output/ (configurable in M0.2)
- JSONata `length()` function not supported (blues/jsonata-go limitation)

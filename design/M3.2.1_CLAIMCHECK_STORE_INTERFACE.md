# M3.2.1 Claim Check Store Interface Design

**Status:** Design Document (M3.2.1 spike)  
**Date:** 2026-09-05  
**Phase:** 3, Milestone 3.2.1 — Claim Check  

## Executive Summary

The Claim Check pattern allows `dimd` to handle arbitrarily large message payloads by storing them externally and carrying only lightweight references in-transit.

**Design Decision:** Reuse the existing S3 sink adapter as the reference backend, following the same "reuse-what-you-already-shipped" pattern M2.6 used for purge-log export.

**Claim-Check Store Interface:**
- Generic storage abstraction (pluggable backends)
- S3 as the reference implementation
- File paths as ticket references (no database needed)
- Payload metadata: size, content-type, checksum (for integrity)

---

## 1. Problem Statement

### Today's Limitations

Currently, `dimd` processes messages end-to-end with the full payload:
- **Large attachments** (PDFs, images, archives) → payload travels through every step
- **Every step** processes the attachment, even if not needed (e.g., routing decision doesn't look at attachment)
- **Lineage records** inline the full payload → storage overhead, slow queries
- **Network overhead** → attachment crosses every network boundary in the pipeline

### Use Cases for Claim Check

1. **Order Processing with Attachments**
   - Order message includes invoice PDF (5 MB)
   - Routing step doesn't look at attachment
   - Compliance step needs the PDF
   - Without claim-check: PDF travels through routing, translation, filtering unnecessarily
   - With claim-check: PDF stored once, retrieved only by compliance step

2. **Document Processing Pipeline**
   - Large scanned document (100 MB)
   - Initial steps: extract metadata, OCR, route
   - Storage step: store full document
   - Most steps work on metadata, not full document

3. **Lineage Optimization**
   - 50 MB payload in message
   - Lineage records should capture metadata (hash, size) not the payload
   - Without claim-check: 50 MB × number of records = massive lineage table
   - With claim-check: lineage stores ticket (reference) instead

## 2. Claim Check Pattern Overview

The Claim Check EIP works in three phases:

```
┌─────────────────────────────────────────────────────────────┐
│                        Original Message                     │
│  { order_id: "123", items: [...], invoice: <5 MB PDF> }    │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
                    ┌──────────────────────┐
                    │   Claim Check Step   │
                    │ - Extract payload    │
                    │ - Store in S3        │
                    │ - Generate ticket    │
                    └──────────────────────┘
                              │
                              ▼
┌──────────────────────────────────────────────────────────────┐
│                    Lightweight Message                       │
│  { order_id: "123", items: [...],                            │
│    _claim_check: {                                           │
│      ticket: "s3://bucket/dim/claims/abc123def",             │
│      size: 5242880,                                          │
│      hash: "sha256:...",                                     │
│      content_type: "application/pdf"                         │
│    }}                                                        │
└──────────────────────────────────────────────────────────────┘
                              │
                    ┌─────────┴──────────┐
                    ▼                    ▼
             Routing Step         Compliance Step
           (doesn't use PDF)       (needs PDF)
                    │                    │
                    │         ┌──────────▼──────────┐
                    │         │ Claim Check Resolve │
                    │         │ - Read ticket       │
                    │         │ - Fetch from S3     │
                    │         │ - Restore payload   │
                    │         └────────────────────┘
                    │                    │
                    └────────────────────┤
                                         ▼
                            ┌────────────────────────┐
                            │   Final Message        │
                            │   (payload restored)   │
                            └────────────────────────┘
```

## 3. Store Interface Design

### ClaimCheckStore Interface

```go
type ClaimCheckStore interface {
    // Store saves a payload and returns a ticket reference.
    // The ticket should be human-readable (S3 path) for debugging.
    // Metadata (size, hash, content_type) is stored alongside payload.
    Store(ctx context.Context, payload []byte, metadata ClaimCheckMetadata) (ticket string, error)

    // Retrieve loads a payload using the ticket.
    // Returns the full payload and metadata.
    Retrieve(ctx context.Context, ticket string) (payload []byte, metadata ClaimCheckMetadata, error)

    // Delete removes a stored payload (for garbage collection).
    Delete(ctx context.Context, ticket string) error

    // Verify checks integrity of a stored payload (checksum match).
    Verify(ctx context.Context, ticket string, expectedHash string) (bool, error)

    // Close gracefully shuts down the store.
    Close(ctx context.Context) error
}
```

### ClaimCheckMetadata

```go
type ClaimCheckMetadata struct {
    ContentType string    // MIME type (e.g., "application/pdf")
    Size        int64     // Payload size in bytes
    Hash        string    // SHA256 hash for integrity
    Timestamp   time.Time // When stored
    ExpiresAt   time.Time // Optional expiration for garbage collection
}
```

### Ticket Format

Tickets are S3 paths with a predictable structure:

```
s3://bucket/dim/claims/{timestamp}/{instance-id}/{random-id}
```

Example:
```
s3://my-bucket/dim/claims/2026-09-05/dimd-1/abc123def456789
```

**Why this format:**
- Human-readable (operators can see timestamp and instance)
- Sortable (prefix queries for cleanup)
- Instance-tagged (helps with multi-instance debugging)
- No database lookups needed (ticket is self-describing)

## 4. Reference Implementation: S3 Backend

### Why Reuse S3?

`dimd` already has a production S3 sink adapter:
- Proven authentication (IAM, SigV4, cross-account)
- Battle-tested concurrent writes
- ✅ Already in codebase, no new dependency
- ✅ Follows "reuse what you already shipped" pattern (see M2.6 purge-log export)

### S3DedupStore Implementation (Pseudocode)

```go
type S3ClaimCheckStore struct {
    client    *s3.Client
    bucket    string
    region    string
    retries   int
}

func (s *S3ClaimCheckStore) Store(ctx context.Context, payload []byte, metadata ClaimCheckMetadata) (string, error) {
    // Generate ticket (path)
    ticket := s.generateTicket()
    
    // Calculate hash if not provided
    if metadata.Hash == "" {
        metadata.Hash = "sha256:" + sha256(payload)
    }
    
    // Upload to S3 with metadata in object tags/headers
    err := s.client.PutObject(ctx, &s3.PutObjectInput{
        Bucket: aws.String(s.bucket),
        Key:    aws.String(ticket),
        Body:   bytes.NewReader(payload),
        ContentType: aws.String(metadata.ContentType),
        // Custom metadata in object tags or headers
        Metadata: map[string]string{
            "claim-check-hash": metadata.Hash,
            "claim-check-size": strconv.FormatInt(metadata.Size, 10),
        },
    })
    
    if err != nil {
        return "", fmt.Errorf("store failed: %w", err)
    }
    
    return ticket, nil
}

func (s *S3ClaimCheckStore) Retrieve(ctx context.Context, ticket string) ([]byte, ClaimCheckMetadata, error) {
    // Download from S3
    obj, err := s.client.GetObject(ctx, &s3.GetObjectInput{
        Bucket: aws.String(s.bucket),
        Key:    aws.String(ticket),
    })
    // ...
    
    payload, _ := io.ReadAll(obj.Body)
    
    // Extract metadata from headers/tags
    metadata := ClaimCheckMetadata{
        ContentType: aws.ToString(obj.ContentType),
        Size:        aws.ToInt64(obj.ContentLength),
        Hash:        obj.Metadata["claim-check-hash"],
    }
    
    return payload, metadata, nil
}
```

## 5. Integration Points

### Where Claim Check Fits in Pipeline

```
Route Definition:
┌──────────────────┐
│  sources         │
├──────────────────┤
│  - http          │
├──────────────────┤
│  steps           │
│  - translate     │
│  - filter        │
│  - claim_check   │  ← M3.2.2: new step (stores large payload)
│  - translate     │
│  - claim_resolve │  ← M3.2.3: resolves ticket back to payload
├──────────────────┤
│  sinks           │
│  - http          │
└──────────────────┘
```

### M3.2.2 Integration (claim_check step)
- Step receives message with large payload
- Calls `ClaimCheckStore.Store(payload)`
- Gets back ticket reference
- Replaces message body with lightweight structure containing ticket
- Passes modified message downstream

### M3.2.3 Integration (claim_resolve step)
- Step receives message with ticket reference
- Calls `ClaimCheckStore.Retrieve(ticket)`
- Gets back full payload
- Restores message body to original state (or uses payload in logic)

### Lineage Integration
- When storing lineage record: use ticket, not payload
- Lineage record includes: message ID, route, subject, **ticket reference**
- Operators can look up full payload via ticket if needed (no payload in DB)

## 6. Tradeoffs & Design Decisions

| Tradeoff | Choice | Rationale |
|----------|--------|-----------|
| **Storage backend** | S3 (reusable) | Already in codebase; proven; no new dependency |
| **Ticket format** | S3 path (self-describing) | No database lookups; human-readable; sortable |
| **Metadata storage** | Object tags/headers | S3-native; no extra table; queryable via S3 API |
| **Verification** | Checksum on retrieve | Ensures integrity; cheap (hash payload on read) |
| **Deletion** | Manual via Delete() | Garbage collection per policy (not automatic) |
| **Expiration** | Optional in metadata | Can implement TTL cleanup separately |
| **Concurrent access** | S3 handles natively | Multiple instances can read same ticket safely |

---

## 7. Failure Modes & Resilience

### S3 Unavailable
- **Claim Check step fails** → message fails (same as if S3 sink fails)
- **Claim Resolve step fails** → downstream unable to process (graceful degradation)
- **Recovery:** Retry with exponential backoff (standard S3 pattern)

### Missing Ticket
- **Claim Resolve step fails** → log error, message fails (not silently dropped)
- **Prevention:** Verify ticket exists before returning from Claim Check step

### Payload Tampered
- **Verify() detects checksum mismatch** → fail fast (integrity check)
- **Prevention:** Store hash, verify on retrieve

### Large Payload (GBs)
- **S3 handles streaming** → no in-memory buffer needed
- **MultipartUpload for large payloads** (>100MB) implemented in S3 backend

---

## 8. Comparison with Alternatives

| Approach | Pros | Cons |
|----------|------|------|
| **S3 Backend (chosen)** | Reuse existing; proven; scalable | Requires AWS credentials |
| **Local Filesystem** | Simple; no external dependency | Single-instance only; slow; no HA |
| **Database (Postgres BYTEA)** | Central; transactional | Slow for large payloads; disk-heavy |
| **Redis (ephemeral)** | Fast; distributed | Limited by memory; loses data on restart |
| **IPFS/Distributed** | Content-addressable; immutable | Overkill; slow; operational complexity |

**Decision:** S3 is the right balance of simplicity, scalability, and reusability.

## 9. Configuration & Deployment

### Configuration Structure

```yaml
claim_check:
  backend: "s3"  # or "local" (for single-instance), future: "postgres"
  s3:
    bucket: "dim-claims"
    region: "us-east-1"
    prefix: "dim/claims"  # Optional: namespace within bucket
    expiration_days: 30   # Optional: garbage collection TTL
```

### Minimum Viable Setup
- Single S3 bucket shared across cluster
- IAM policy grants `s3:GetObject`, `s3:PutObject`, `s3:DeleteObject` on `bucket/dim/claims/*`
- No additional database needed

## Summary

M3.2.1 establishes the Claim Check Store abstraction as a pluggable interface with S3 as the reference backend. This reuses proven infrastructure, requires minimal new code, and scales horizontally across instances. The self-describing ticket format (S3 paths) eliminates the need for a separate lookup database, keeping the system operationally simple.

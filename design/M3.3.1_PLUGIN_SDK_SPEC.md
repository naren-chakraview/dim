# Plugin SDK Specification — dim Function Plugin Contract

**Version:** 1.0  
**Date:** 2026-09-06  
**Status:** Formal specification for Phase 3 (M3.3.1)  
**Author:** dim Team

## Executive Summary

This document defines the neutral, engine-agnostic contract between dim and third-party function plugins. A **plugin** is an external function that performs computation within a `translate`, `filter`, `authorize`, or custom step — either as a native compiled Go binary communicating via RPC, or as a WebAssembly (WASM) module running in a managed sandbox.

This specification covers:
- **Native plugins** via `hashicorp/go-plugin` (subprocess-based RPC)
- **WASM plugins** via `wazero` (in-process, sandboxed)

Both surfaces conform to a single logical contract: a function that accepts structured input, performs computation, and returns structured output — with no requirement to read dim's internal code or rely on internal packages.

---

## 1. Core Concepts

### 1.1 Function Plugin

A **function plugin** is a reusable, named unit of computation that:
- Accepts zero or more **input arguments** (JSON-serializable)
- Performs domain-specific logic
- Returns a **single result** (JSON-serializable)
- May fail with an error

Examples:
- `enrichment/fetch_customer_details` — HTTP call to customer DB
- `validation/validate_credit_card` — PCI compliance check
- `transform/normalize_phone` — Format normalization
- `security/decrypt_field` — Field-level decryption

### 1.2 Plugin Runtime

The **runtime** is the execution environment:
- **Native**: A subprocess managed by `hashicorp/go-plugin`, communicating via JSON-RPC
- **WASM**: An in-process module instance managed by `wazero`

A single `dimd` instance may load multiple plugins of either runtime.

### 1.3 Plugin Lifecycle

1. **Discovery**: Route configuration specifies plugin by name/location
2. **Loading**: Plugin runtime loads binary or WASM module
3. **Registration**: Plugin is registered in the functions registry
4. **Invocation**: Steps call the plugin as needed via the registry
5. **Unloading**: Plugin process killed or module deallocated on shutdown

## 2. Contract Specification

### 2.1 Shared Logical Interface

Both native and WASM plugins conform to this logical contract:

```go
// Function represents a callable plugin function
type Function interface {
	// Call executes the function with the given arguments
	// Returns the result (JSON-serializable) or an error
	Call(ctx context.Context, args ...interface{}) (interface{}, error)
}
```

Key invariants:
- **Determinism**: Same inputs must always produce same outputs (for lineage/replay correctness)
- **Isolation**: No side effects; plugin state is ephemeral per invocation
- **Timeouts**: Calls must respect a configurable timeout (default: 5 seconds)
- **Error handling**: Failures return (nil, error) — not panics or silent failures

### 2.2 Native Plugin Contract (Go RPC)

#### 2.2.1 Binary Interface

A native plugin is a **standalone executable** that:
1. Starts as a subprocess
2. Communicates via JSON-RPC over stdio/network
3. Implements the handshake protocol below
4. Responds to function calls until shutdown

#### 2.2.2 Handshake Protocol

Before any function calls, the plugin and host exchange a handshake:

```go
// Handshake configuration (shared between plugin and host)
HandshakeConfig{
    ProtocolVersion:  1,
    MagicCookieKey:   "DIM_PLUGIN",
    MagicCookieValue: "dim-function-plugin-v1",
}
```

**Handshake steps:**
1. Host writes `MagicCookieKey=MagicCookieValue` to plugin's env
2. Plugin verifies env variable on startup
3. Plugin outputs `magic cookie value` to stdout
4. Host verifies magic cookie and establishes RPC connection
5. If mismatch: plugin exits with code 1, host reports error

**Why?** Ensures plugin binary is actually a dim plugin (not an arbitrary binary), preventing signature mismatches.

#### 2.2.3 RPC Interface

The plugin exposes a single RPC service with this method signature:

```go
// FunctionService is the RPC service name
const FunctionServiceName = "Plugin"

// FunctionCall is the RPC method signature
type FunctionCall struct {
    Name string
    Args []interface{}
}

type FunctionResponse struct {
    Result interface{}
    Error  string  // Non-empty if call failed
}

// Method: Plugin.Call(FunctionCall) FunctionResponse
```

**Call semantics:**
- **Name**: Function name to invoke (e.g., `validate_email`)
- **Args**: JSON-serializable arguments (array, may be empty)
- **Result**: JSON-serializable output
- **Error**: Non-empty string if call failed; Result is null if Error is set

#### 2.2.4 Example Native Plugin Interaction

```
Host → Plugin (establish RPC connection)

Host.RPC Call:
  Service: "Plugin"
  Method:  "Call"
  Args: {
    Name: "enrich_customer",
    Args: [ {"customer_id": "cust-123"} ]
  }

Plugin.RPC Response:
  Result: {
    "name": "Alice",
    "tier": "premium",
    "balance": 5000.00
  }
  Error: ""

Host.RPC Call (error case):
  Service: "Plugin"
  Method:  "Call"
  Args: {
    Name: "validate_card",
    Args: [ {"card": "invalid"} ]
  }

Plugin.RPC Response:
  Result: null
  Error: "invalid card format: does not match regex"
```

#### 2.2.5 Plugin Binary Requirements

A native plugin binary must:

1. **Check magic cookie on startup**
   ```go
   if os.Getenv("DIM_PLUGIN") != "dim-function-plugin-v1" {
       log.Fatal("Not a dim plugin")
   }
   ```

2. **Print magic cookie to stdout**
   ```go
   fmt.Println(os.Getenv("DIM_PLUGIN"))
   ```

3. **Expose the Plugin.Call RPC method**
   - Listen on a port provided by hashicorp/go-plugin
   - Handle multiple concurrent calls (thread-safe)

4. **Implement one or more named functions**
   - Each function has a Name and implementation
   - Functions are queried by Name in Call requests
   - Unknown function names return an error, not a crash

5. **Handle context.Context cancellation**
   - Respect timeouts passed via RPC context
   - Clean up resources on cancellation

#### 2.2.6 Communication Details

- **Transport**: Subprocess stdout/stderr + plugin-provided network port
- **Protocol**: JSON-RPC 2.0 over net.Conn (TCP or Unix socket)
- **Marshaling**: Standard Go `encoding/json`
- **Errors**: JSON-RPC error responses are translated to Go error values

### 2.3 WASM Plugin Contract

#### 2.3.1 Module Interface

A WASM plugin is a **WebAssembly module** that:
1. Exports named functions matching the WASM ABI (§2.3.2)
2. Is loaded into `wazero` runtime
3. Responds to function calls with structured output

#### 2.3.2 WASM ABI (Application Binary Interface)

WASM modules must follow this ABI for function calls:

**Input/Output via Linear Memory:**

All WASM plugins use linear memory for structured data. Function calls work as follows:

1. **Marshaling arguments to memory:**
   - Host serializes input args to JSON bytes
   - Host writes bytes to a buffer in module memory (via `malloc` helper)
   - Host calls exported function with pointer and length

2. **Function invocation:**
   - Function is called with two i32 parameters:
     - `args_ptr`: Memory pointer to JSON-serialized arguments
     - `args_len`: Byte length of arguments
   - Function reads from memory, processes, writes result to memory
   - Function returns two i32 values:
     - `result_ptr`: Memory pointer to JSON-serialized result
     - `result_len`: Byte length of result

3. **Reading result from memory:**
   - Host reads `result_len` bytes from `result_ptr`
   - Deserializes JSON back to Go value
   - Frees the result buffer (module responsibility or host via `free`)

**Function Signature (Wat notation):**

```wasm
(func $my_function (export "my_function")
  (param $args_ptr i32)
  (param $args_len i32)
  (result i32 i32)  ;; returns (result_ptr, result_len)
)
```

**Error Handling in WASM:**

Errors are communicated via JSON serialization:
- On success: `{"result": <value>}`
- On error: `{"error": "error message"}`

The host deserializes and interprets this structure.

#### 2.3.3 Memory Management

WASM modules must implement two memory helper functions:

```wasm
(memory (export "memory") 1)  ;; At least 1 page (64 KB)

(func (export "malloc") (param $size i32) (result i32)
  ;; Allocate size bytes, return pointer
)

(func (export "free") (param $ptr i32) (param $size i32)
  ;; Deallocate memory at ptr of length size
)
```

**Rationale**: Allows host to allocate/free memory in module's linear memory space, avoiding dangling pointers.

#### 2.3.4 Example WASM Function (Pseudocode)

```rust
// Rust + wasm32-unknown-unknown target

#[no_mangle]
pub extern "C" fn validate_email(args_ptr: i32, args_len: i32) -> (i32, i32) {
    // 1. Read arguments from memory
    let args_bytes = unsafe {
        std::slice::from_raw_parts(args_ptr as *const u8, args_len as usize)
    };
    
    // 2. Parse JSON
    let args: Vec<String> = serde_json::from_slice(args_bytes)
        .expect("valid json");
    
    let email = &args[0];
    
    // 3. Validate
    let is_valid = email.contains("@");
    
    // 4. Serialize result to memory
    let result = json!({"result": is_valid});
    let result_bytes = serde_json::to_vec(&result).unwrap();
    
    // 5. Copy to module memory (via malloc)
    let result_ptr = malloc(result_bytes.len());
    unsafe {
        std::ptr::copy_nonoverlapping(
            result_bytes.as_ptr(),
            result_ptr as *mut u8,
            result_bytes.len()
        );
    }
    
    // 6. Return (ptr, len)
    (result_ptr as i32, result_bytes.len() as i32)
}
```

#### 2.3.5 WASM Module Requirements

A WASM module must:

1. **Export functions** with signature `(i32, i32) -> (i32, i32)`
2. **Export linear memory** accessible to host
3. **Implement malloc/free** for memory management
4. **Serialize/deserialize JSON** in its implementation language
5. **Return errors** as JSON-serialized `{"error": "message"}`
6. **Be deterministic**: Same inputs → same outputs (no floating point, randomness, or side effects)
7. **Respect memory limits**: Allocate conservatively; avoid unbounded loops

## 3. Plugin Discovery and Loading

### 3.1 Plugin Specification in Route Config

Plugins are referenced in route step configs:

```yaml
routes:
  order-processing:
    steps:
      - type: translate
        spec:
          expression: $enrich_customer({"customer_id": message.customer_id})
          functions:
            - name: enrich_customer
              type: plugin
              runtime: native           # or "wasm"
              ref: /usr/local/bin/dim-plugins/enrich  # or path/to/module.wasm
              timeout: 5s              # optional, default 5s
```

### 3.2 Loading Mechanism

1. **At route startup:**
   - Resolve plugin reference to actual binary/WASM path
   - Load plugin via appropriate runtime (native or WASM)
   - Register in functions registry

2. **On first invocation:**
   - Plugin call goes through functions registry
   - Runtime marshals arguments, calls plugin
   - Result unmarshaled and returned to step

3. **On shutdown:**
   - Native: Kill plugin subprocess
   - WASM: Module deallocated when runtime closes

### 3.3 Plugin Resolution

Plugin references are resolved in this order:
1. Relative to route config file location
2. Absolute path (if provided)
3. System PATH (for native binaries only)
4. Plugin registry directory (configurable, e.g., `/etc/dim/plugins`)

## 4. Version Contract

### 4.1 Versioning Strategy

The plugin SDK version is **independent of the engine version**, matching the pattern M1.1 established for the PDP contract.

**Version format:** `MAJOR.MINOR.PATCH`

- **Major version** (e.g., 1 → 2): Breaking changes to the ABI or RPC interface
- **Minor version** (e.g., 1.0 → 1.1): Backward-compatible additions (new context fields, new optional parameters)
- **Patch version** (e.g., 1.0 → 1.0.1): Clarifications or bug fixes, no semantic changes

### 4.2 Version Negotiation

Before any function calls, host and plugin agree on SDK version:

**Native plugins:**
- Handshake includes `ProtocolVersion: 1`
- RPC calls include SDK version in metadata
- If versions don't match, call fails with error

**WASM plugins:**
- Version checked via module export (e.g., `get_sdk_version() -> i32`)
- If version mismatch, instantiation fails

### 4.3 Backward Compatibility Promise

A plugin built against SDK v1.0 **will continue to work** with engine versions shipping SDK v1.x (1.0, 1.1, 1.2, etc.).

Breaking changes only happen at major version boundaries (1 → 2).

## 5. Go SDK Interface (`pkg/sdk`)

### 5.1 Public Types

The public SDK exposes these types (no internal imports required):

```go
package sdk

import "context"

// Function is the core interface all plugins must implement
type Function interface {
    // Call executes the plugin with the given arguments
    // ctx: cancellation context (respects timeout)
    // args: JSON-serializable input arguments (may be empty)
    // Returns: JSON-serializable result, or error if call failed
    Call(ctx context.Context, args ...interface{}) (interface{}, error)
}

// FunctionDef describes a plugin function for registration
type FunctionDef struct {
    Name    string       // Function name (e.g., "validate_email")
    Runtime string       // "native" or "wasm"
    Ref     string       // Reference (path, URL, etc.)
    Version string       // SDK version this plugin targets (e.g., "1.0")
    Timeout time.Duration // Call timeout (default: 5s)
}

// Registry is the function registry where plugins register themselves
type Registry interface {
    // Register adds a function to the registry
    Register(def FunctionDef, impl Function) error
    
    // Get retrieves a registered function by name
    Get(name string) (Function, error)
    
    // List returns all registered function names
    List() []string
}

// PluginLoader loads plugins from binary/WASM
type PluginLoader interface {
    // Load a plugin from a reference (path/URL)
    // Returns a Function ready to call
    Load(ctx context.Context, def FunctionDef) (Function, error)
    
    // Unload cleans up resources
    Unload(name string) error
    
    // Close shuts down the runtime
    Close() error
}
```

### 5.2 Helper Functions

```go
package sdk

// LoadPlugin is a convenience function for loading a single plugin
func LoadPlugin(ctx context.Context, ref string, runtime string) (Function, error)

// CallFunction is a convenience for single function invocation
func CallFunction(ctx context.Context, fn Function, args ...interface{}) (interface{}, error)

// SDKVersion returns the current SDK version
func SDKVersion() string // e.g., "1.0"
```

## 6. Conformance Requirements

### 6.1 Native Plugin Requirements

A native plugin must:

1. ✅ Implement the handshake protocol (check magic cookie)
2. ✅ Export a `Plugin.Call` RPC method
3. ✅ Accept `FunctionCall` structs with Name and Args
4. ✅ Return `FunctionResponse` with Result or Error
5. ✅ Be deterministic (same inputs → same outputs)
6. ✅ Handle context cancellation (via timeouts)
7. ✅ Use only provided interfaces, no dim internal imports
8. ✅ Support graceful shutdown on SIGTERM

### 6.2 WASM Plugin Requirements

A WASM module must:

1. ✅ Export named functions with signature `(i32, i32) -> (i32, i32)`
2. ✅ Export linear memory
3. ✅ Implement malloc/free for memory management
4. ✅ Serialize/deserialize JSON for I/O
5. ✅ Return errors as `{"error": "message"}` in JSON
6. ✅ Be deterministic (no float, random, side effects)
7. ✅ Include SDK version (queryable via export)

### 6.3 Testing Conformance

To validate a plugin conforms to this contract:

```bash
# Native plugin
dimctl plugin test --native /path/to/plugin

# WASM plugin
dimctl plugin test --wasm /path/to/module.wasm
```

The conformance test verifies:
- Handshake (native) / exports (WASM)
- Function call execution with example inputs
- Error handling on invalid inputs
- Timeout behavior
- Output serialization correctness

## 7. Example: Third-Party Plugin Implementation

### 7.1 Native Go Plugin Example

```go
// File: cmd/enrich-plugin/main.go

package main

import (
    "context"
    "encoding/json"
    "log"
    "os"
    "fmt"

    "github.com/hashicorp/go-plugin"
    "github.com/naren-chakraview/dim/pkg/sdk"
)

// EnrichmentPlugin implements the dim plugin interface
type EnrichmentPlugin struct {}

func (p *EnrichmentPlugin) Call(ctx context.Context, args ...interface{}) (interface{}, error) {
    // Parse input
    if len(args) < 1 {
        return nil, fmt.Errorf("expected 1 argument")
    }

    var req map[string]interface{}
    reqBytes, _ := json.Marshal(args[0])
    json.Unmarshal(reqBytes, &req)

    customerID, ok := req["customer_id"].(string)
    if !ok {
        return nil, fmt.Errorf("customer_id required")
    }

    // Fetch enrichment (e.g., HTTP call)
    enriched := map[string]interface{}{
        "customer_id": customerID,
        "name":        "Alice",
        "tier":        "premium",
    }

    return enriched, nil
}

func main() {
    // Check magic cookie
    if os.Getenv("DIM_PLUGIN") != "dim-function-plugin-v1" {
        log.Fatal("Not a dim plugin")
    }
    fmt.Println(os.Getenv("DIM_PLUGIN"))

    // Serve via RPC
    plugin.Serve(&plugin.ServeConfig{
        HandshakeConfig: plugin.HandshakeConfig{
            ProtocolVersion:  1,
            MagicCookieKey:   "DIM_PLUGIN",
            MagicCookieValue: "dim-function-plugin-v1",
        },
        Plugins: map[string]plugin.Plugin{
            "enrich": &EnrichmentPlugin{},
        },
    })
}
```

### 7.2 WASM Plugin Example (Rust)

```rust
// File: src/lib.rs (wasm32-unknown-unknown target)

use std::ffi::CStr;
use serde_json::{json, Value};

#[no_mangle]
pub fn validate_email(args_ptr: i32, args_len: i32) -> u64 {
    unsafe {
        let args_bytes = std::slice::from_raw_parts(args_ptr as *const u8, args_len as usize);
        let args: Vec<String> = serde_json::from_slice(args_bytes).unwrap_or_default();
        
        let email = args.get(0).map(|s| s.as_str()).unwrap_or("");
        let is_valid = email.contains("@") && email.len() > 3;
        
        let result = json!({"result": is_valid});
        let bytes = serde_json::to_vec(&result).unwrap();
        
        let ptr = malloc(bytes.len() as i32) as *mut u8;
        std::ptr::copy_nonoverlapping(bytes.as_ptr(), ptr, bytes.len());
        
        ((ptr as u32 as u64) << 32) | (bytes.len() as u64)
    }
}

#[no_mangle]
pub fn malloc(size: i32) -> i32 {
    // Simple allocator (for demo; real implementation uses proper allocator)
    static mut HEAP: [u8; 65536] = [0; 65536];
    static mut OFFSET: i32 = 0;
    
    unsafe {
        let ptr = OFFSET;
        OFFSET += size;
        ptr
    }
}

#[no_mangle]
pub fn free(_ptr: i32, _size: i32) {
    // No-op for this simple demo
}

#[no_mangle]
pub fn get_sdk_version() -> i32 {
    1  // SDK version 1.0
}
```

## 8. Design Rationale

### Why separate SDK from engine?

- Plugins are external, third-party code written in arbitrary languages
- SDK is the published contract; engine internals are implementation detail
- Breaking engine changes (refactoring internal packages) shouldn't break plugins

### Why two runtimes?

- **Native (RPC)**: Fast, full computational power, existing infrastructure (hashicorp/go-plugin)
- **WASM**: Sandboxed, safe, portable, no external binary management

Different use cases benefit from each.

### Why versioned independently?

- Engine releases happen on its own cadence
- Plugin SDK changes happen on a different cadence
- Plugin authors need a stable, long-lived target

(This mirrors M1.1's PDP contract approach.)

### Why linear memory + JSON?

- Linear memory is WASM's native I/O mechanism
- JSON is language-neutral, human-inspectable, debuggable
- No need to negotiate serialization format per plugin

### Why RPC for native plugins?

- Process isolation (one bad plugin can't crash the host)
- Version negotiation (plugin and host can disagree on SDK version gracefully)
- Subprocess lifecycle management (clean shutdown, resource cleanup)

## 9. Error Handling

### 9.1 Native Plugin Errors

```go
// Plugin.Call() RPC response with error:
{
    "Result": null,
    "Error": "customer_id not found in customer database"
}

// Host interprets this as:
result, err := fn.Call(ctx, args...)
// err.Error() == "customer_id not found in customer database"
```

### 9.2 WASM Plugin Errors

```json
// Returned from WASM function:
{"error": "customer_id not found in customer database"}

// Host deserializes and interprets as error
```

### 9.3 Timeout Errors

If a plugin call exceeds its timeout (default: 5s):
- **Native**: RPC call is abandoned, host reports "timeout"
- **WASM**: Function execution is interrupted, returns error

## 12. FAQ

**Q: Can a plugin import dim's internal packages?**  
A: No. The SDK is the only public interface. Internal packages are not supported and may change without notice.

**Q: How do I debug a plugin call?**  
A: Native plugins print logs to stderr (captured by dimctl). WASM plugins can use `debug_log()` exports for similar effect.

**Q: Can plugins access dim's lineage store?**  
A: No, by design. Plugins are stateless functions. If you need state, store it externally and fetch it as part of your input.

**Q: What about plugin dependencies?**  
A: Native plugins can bundle dependencies (static linking recommended). WASM plugins must include dependencies in the module.

**Q: Can I make plugin calls nested?**  
A: Yes, but avoid cycles. If plugin A calls plugin B, make sure B doesn't call A.

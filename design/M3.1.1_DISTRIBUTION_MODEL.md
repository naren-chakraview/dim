# M3.1.1 Distribution Model Spike — Design Decision

**Status:** Decision complete, ready for implementation  
**Date:** 2026-09-05  
**Phase:** 3, Milestone 3.1.1 — Distributed/Clustered Mode  

## Executive Summary

This document evaluates three distribution models for clustered `dimd` operation:
1. **Shared-nothing partitioned** — Each instance owns disjoint routes/partitions
2. **Active-active with shared external state** — All instances process same routes, share state backend
3. **Leader-follower with failover** — One primary, standby replicas

**Decision: Active-active with shared external state.**

**Chosen configuration:**
- All instances actively process the same route set
- External state backends (Postgres/Redis) for dedup and optionally lineage
- Platform-agnostic discovery (static config, environment vars, or optional coordination service)
- Works across clouds, on-prem, and hybrid deployments

**Tradeoff accepted:** Requires external state infrastructure. **Benefit:** Scales horizontally, no single point of failure, works everywhere.

---

## 1. Problem Statement

Today `dimd` is single-process with per-instance state:
- In-memory message dedup → duplicates if two instances see same message
- Embedded SQLite lineage store → lineage scattered across instances
- Per-instance hot reload generation tracking → no coordination between instances

When multiple instances process overlapping routes, we need to answer:
1. How do instances coordinate without a mandatory coordination service?
2. How do we ensure no duplicate processing?
3. How do we aggregate lineage/observability across the cluster?
4. What deployment models can we support?

## 2. Evaluation Criteria

### Functional Requirements
- **No duplicate processing** — Same message reaching two instances must be deduplicated
- **Cross-instance lineage** — Queryable audit trail across cluster, not per-instance exports
- **Coordinated hot reload** — Config changes propagate, with predictable rollout semantics
- **Cluster membership** — Clear answer for "what is the cluster" (static, dynamic, external discovery)

### Non-Functional Requirements (Platform-Agnostic)
- **Cloud-agnostic** — Works on AWS, GCP, Azure without assuming managed services
- **On-prem compatible** — No forced cloud vendor lock-in or SaaS dependencies
- **Hybrid deployments** — Can span on-prem + cloud without special treatment
- **Fail-safe defaults** — Degrades gracefully if external dependencies fail
- **Operational simplicity** — Reasonable complexity for typical ops teams to manage

## 3. Model Evaluation

### 3.1 Shared-Nothing Partitioned

**Model:** Each instance owns a disjoint subset of routes. Instance A handles routes {a, b}; Instance B handles {c, d}. Assignment is static (config) or dynamic (coordinator assigns).

#### How It Works
```
Request for route X
  └─→ Load balancer / client → Instance A (if route X ∈ A's partition)
      └─→ Process locally, emit lineage locally
```

#### Advantages
- ✅ No external state needed (single-instance model scales horizontally)
- ✅ Zero cross-instance coordination
- ✅ No duplicate processing by design
- ✅ Simple to reason about ("this instance owns these routes")

#### Disadvantages
- ❌ **Operator burden:** Route assignment must stay in sync across cluster (static: manual, dynamic: needs coordinator)
- ❌ **Load skew:** Can't rebalance without downtime (some routes get traffic spikes)
- ❌ **Failover complexity:** If Instance A dies, routes a/b become unavailable unless pre-assigned to standby
- ❌ **Cascading blast radius:** One instance's overload doesn't affect others (good), but loss of one instance loses those routes (bad)
- ❌ **Multi-cloud hard:** Route assignment logic becomes cloud-specific; cross-cloud hybrid very difficult

#### Deployment Model
- Single cloud: Viable (assign routes to Kubernetes nodes/ASGs, or static config)
- Multi-cloud: Difficult (need coordinator or per-cloud routing logic)
- On-prem: Possible with static config, but assignment is manual and error-prone
- Hybrid: ❌ Not recommended (route assignment spans infrastructure boundary)

#### Verdict
**Rejected.** Partitioning sidesteps clustering rather than solving it. Works for simple, single-cloud deployments but creates operational friction at scale and fails the multi-cloud/hybrid requirement.

---

### 3.2 Active-Active with Shared External State

**Model:** All instances process all routes. External backend (database, cache) holds shared state: dedup store, optionally lineage.

#### How It Works
```
Request for message M
  └─→ Any instance (load balancer, client round-robin)
      ├─→ Check dedup store (Redis/Postgres): "Have we seen M before?"
      │   ├─ Yes → Skip processing, return early
      │   └─ No → Lock key, process, emit lineage to shared store, mark deduplicated
      └─→ Continue
```

#### Advantages
- ✅ **Simple model:** All instances are equal, any can handle any route
- ✅ **Horizontal scaling:** Add instances, traffic spreads automatically
- ✅ **No single point of failure:** One instance dies → traffic redistributes
- ✅ **Hybrid-friendly:** Instances in different clouds/regions all see same dedup state
- ✅ **Flexible discovery:** Static config, env vars, or optional coordinator (etcd/Consul) — implementation choice, not architecture requirement
- ✅ **Lineage aggregation:** Natural (all lineage in one store)
- ✅ **Operational simplicity:** "Deploy N instances, point them at Postgres, they work"

#### Disadvantages
- ❌ **External dependency:** Requires Postgres/Redis/etc. (but can be RDS, managed Redis, on-prem PostgreSQL)
- ❌ **Contention on dedup store:** High-throughput routes hit dedup store on every message (mitigated by local cache + async replication for lineage)
- ❌ **Latency added:** Dedup check adds round-trip to external store (typically <10ms for RDS/managed Redis)
- ⚠️ **Failover in dedup store:** If external store is down, cluster degrades (no dedup) but continues operating

#### Deployment Model
- Single cloud: ✅ Excellent (RDS, ElastiCache, managed services)
- Multi-cloud: ✅ Good (point all instances at same external DB, or use per-region replicas)
- On-prem: ✅ Good (PostgreSQL VM, Redis instance, even consumer-grade hardware)
- Hybrid: ✅ Excellent (all instances see same dedup state regardless of where they run)

#### Failure Modes
- External store down → Dedup disabled, but processing continues (acceptable trade)
- Network partition → Dedup becomes local, risks duplicates (mitigated by eventual consistency + idempotence)

#### Verdict
**Chosen.** Best balance of simplicity, scalability, and cross-platform support.

### 3.3 Leader-Follower with Failover

**Model:** One primary instance processes all routes, replicates state (lineage, dedup) to standby replicas. On primary failure, standby promotes.

#### How It Works
```
Primary instance
  ├─→ Process all routes, build dedup store, emit lineage
  └─→ Replicate state to Standby A, Standby B
      └─→ On primary health check fail → Standby A promoted (via coordinator: etcd/Consul, or DNS failover)
```

#### Advantages
- ✅ **No external store needed** (state replicated between instances)
- ✅ **Familiar pattern** (replication, failover well-understood)
- ✅ **No contention** (primary is single writer for dedup)

#### Disadvantages
- ❌ **Underutilized replicas:** Standbys sit idle until failover (wasteful for HA, not HA-cost-effective)
- ❌ **Failover complexity:** Needs a coordinator (etcd/Consul) or DNS magic to detect failure and promote
  - Coordinator → Requires deployment and operation of coordination service (defeats "no coordination assumed")
  - DNS → Slow failover (DNS TTL, propagation delays), not suitable for <10s failover SLAs
- ❌ **Replication lag:** Standby may lag behind primary, risking message loss on failover
- ❌ **Single active instance:** No horizontal scaling benefit; can't spread load across replicas
- ❌ **Multi-cloud nightmare:** Replication across clouds is slow; failover latency unacceptable; state divergence risks

#### Deployment Model
- Single cloud: ⚠️ Possible (coordinator service, or DNS failover) but adds operational burden
- Multi-cloud: ❌ Not recommended (replication latency, failover SLAs don't hold, state divergence risk)
- On-prem: ⚠️ Possible (local coordinator or DNS, similar burden as single-cloud)
- Hybrid: ❌ Not viable (cross-site failover latency rules this out)

#### Verdict
**Rejected.** Doesn't meet multi-cloud/hybrid requirement. Best for single-site HA, but simpler to solve with active-active + managed external store.

## 4. Tradeoff Analysis

### Tradeoff: External Dependency vs. Operational Simplicity

**Active-active requires external state backend (Postgres/Redis).** This is a tradeoff, but a good one:

| Aspect | Shared-Nothing | Active-Active | Leader-Follower |
|--------|---|---|---|
| External dependency | None | Postgres/Redis | Coordinator (etcd/Consul) |
| Operational burden | High (route management) | Medium (DB ops, familiar) | High (coordinator + replication) |
| Horizontal scaling | Limited | Unlimited | None (passive replicas) |
| Multi-cloud | Difficult | Easy | Hard |
| Failover SLA | Hours (reassign routes) | Seconds (DB HA) | Minutes (DNS) or seconds (coordinator) |

**Conclusion:** Active-active's external dependency is a known pattern (every web app uses a database). Postgres/Redis are boring, well-understood infrastructure. Coordinator services (etcd, Consul) are not, and add operational complexity to achieve worse scaling properties.

## 5. Platform Evaluation

### Target Platforms Evaluated

1. **AWS (ECS, EC2)**
   - External state: RDS PostgreSQL ✅ (managed, HA, replicated)
   - Instance discovery: Environment variables ✅ (task metadata)
   - Deployment model: Simple (launch N tasks, all point to RDS)

2. **GCP (Cloud Run, Compute Engine)**
   - External state: Cloud SQL ✅ (managed Postgres, HA)
   - Instance discovery: Env vars ✅ (service metadata)
   - Deployment model: Simple (scale service, all replicas point to Cloud SQL)

3. **Azure (App Service, Container Instances)**
   - External state: Azure Database for PostgreSQL ✅ (managed HA)
   - Instance discovery: Env vars ✅ (scale set metadata)
   - Deployment model: Simple (scale, all instances see same DB)

4. **On-Prem (bare metal, VM cluster)**
   - External state: PostgreSQL VM, Redis node ✅ (can co-locate or separate)
   - Instance discovery: Static config ✅ (hardcoded cluster membership in config)
   - Deployment model: Simple (assign static IPs/hostnames, config points to them)

5. **Hybrid (on-prem + AWS)**
   - External state: RDS ✅ (accessible from on-prem via VPN/VPC peering)
   - Instance discovery: Static config ✅ (on-prem instance IP + AWS task IPs in config)
   - Deployment model: Simple (shared config references all instances)

### Platform-Agnostic Discovery

**Cluster membership must work everywhere:**

Option A: **Static config** (simplest)
```yaml
# dimd-cluster.yaml
cluster:
  instances:
    - host: 10.0.1.5     # On-prem
      port: 8080
    - host: 10.2.3.4     # AWS
      port: 8080
```
- ✅ Works everywhere
- ❌ Manual updates on scaling (ops team updates config, redeploy)

Option B: **Environment variables** (cloud-native)
```bash
DIMD_CLUSTER_HOSTS="10.0.1.5:8080,10.2.3.4:8080"
```
- ✅ Works in container orchestration (k8s, ECS, etc)
- ✅ Simple to script
- ❌ Requires orchestration to set env var on scale events

Option C: **Optional coordinator service** (future enhancement)
- If operator wants dynamic discovery: etcd/Consul optional
- If not: static config + env vars sufficient
- Architecture remains agnostic; coordinator is implementation detail

**Decision:** Start with Option A (static) + Option B (env vars). Option C deferred to M3.1.5 if needed.

## 7. Risk Mitigation

| Risk | Mitigation |
|------|---|
| External store becomes bottleneck | Cache dedup locally, async lineage writes; benchmark early (M3.1.2) |
| Replication lag in lineage | Accept eventual consistency; querying lineage waits for replication |
| Failover of external store | Standard RDS/managed DB HA; automatic failover built-in |
| Network partition between instance and store | Instance buffers dedup checks, risks duplicates; acceptable tradeoff |
| Single-cloud assumption creeps in later | Enforce in code review: no cloud-specific APIs in dedup/discovery logic |

---

## 8. Conclusion

**Active-active with shared external state** is the chosen model for M3.1.

**What this means:**
- All `dimd` instances are equal and actively process routes
- Dedup and lineage are centralized in Postgres/Redis
- Instances discover each other via static config or environment variables
- Scales horizontally: add instances, they auto-join the cluster
- Works across AWS, GCP, Azure, on-prem, and hybrid deployments

**Next steps:**
- M3.1.2: Implement dedup store interface
- M3.1.3: Implement lineage store backend
- M3.1.4: Coordinated hot reload
- M3.1.5: Optional coordinator service

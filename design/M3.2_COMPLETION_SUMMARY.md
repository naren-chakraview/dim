## Overview

M3.2 implements the Claim Check Enterprise Integration Pattern, enabling `dimd` to handle arbitrarily large message payloads by storing them externally and carrying only lightweight references in transit.

**Key Achievement:** Large payloads (5MB+ PDFs, document packages) can now bypass the processing pipeline and be retrieved only when needed by downstream steps, eliminating unnecessary network overhead and storage pressure.

## Architecture

### Message Flow: Order Processing with Attachment

```
Original Message
├── order_id: "ORD-2026-001"
├── customer: "ACME Corp"
├── amount: 50000.00
└── invoice_pdf: <5 MB binary>
        ↓
   [Claim Check Step]
   • Store payload in S3/memory
   • Generate ticket: mem://claim-check/1788724869/xyz
   • Compute SHA256(payload)
        ↓
Lightweight Message
├── order_id: "ORD-2026-001"
├── customer: "ACME Corp"
├── amount: 50000.00
└── _claim_check:
    ├── ticket: "mem://claim-check/1788724869/xyz"
    ├── size: 5242951
    ├── hash: "sha256:..."
    └── content_type: "application/pdf"
        ↓
   [Pipeline: Routing, Filtering, Translation]
   • No 5MB PDF in transit
   • Correlation ID preserved
        ↓
   [Compliance Step]
   Needs full invoice for validation
        ↓
   [Claim Resolve Step]
   • Retrieve from store using ticket
   • Verify integrity (hash check)
   • Restore payload
        ↓
Full Message (payload restored)
└── invoice_pdf: <5 MB binary>
```

## Design Decisions & Tradeoffs

### Why In-Memory Store for Testing?
- Fast unit test execution (no I/O)
- No external dependencies
- Deterministic behavior for testing
- Drop-in replacement for production S3 backend

### Why Self-Describing Ticket Format?
- No database lookups needed
- Human-readable for debugging
- Sortable by timestamp (prefix queries)
- Instance-tagged for multi-instance debugging
- S3 paths are first-class citizens (no abstraction needed)

### Why SHA256 Hashing?
- Industry standard for integrity verification
- Fast computation (1-2ms for 5MB payload)
- Efficient storage (64-byte hex string)
- Detects accidental corruption or tampering
- Verification optional but recommended

### Why Payload Removal Configurable?
- Some use cases need both ticket and payload
- Others prefer lightweight messages for network efficiency
- Allows gradual migration from non-claim-checked to claim-checked messages

# Multi-Tenant Resource Accounting Design — Blast Radius Containment

**Version:** 1.0  
**Date:** 2026-09-06  
**Status:** Design specification for Phase 3 (M3.4.1)  
**Author:** dim Team

## Executive Summary

This document designs per-tenant resource accounting for `dimd` to safely share a single instance among multiple domains/tenants. A deliberately overloaded tenant should not degrade another tenant's route performance.

**Core Concept:** Resource quotas keyed on the `domain:` label already present in the reference architecture, with enforcement at three levels:
1. **Message rate limits** — Throttle inbound message rate per domain
2. **Worker pool partitioning** — Reserve execution capacity per domain
3. **Lineage storage quotas** — Cap lineage records per domain

**Design Goal:** Isolation without operational complexity — operators should set quotas once and have them work across all routes.

---

## 1. Problem Statement

### Today's Limitation

Currently, `dimd` processes all domains on the same instance with shared resources:
- Single message queue (no per-domain backpressure)
- Single worker pool (one domain's traffic can starve another)
- Shared lineage store (no quotas; runaway stores impact all queries)
- No observability into per-domain resource use

### The Blast Radius Problem

A single overloaded domain can degrade all others:

```
Instance with Shared Resources:
┌─────────────────────────────────┐
│ Domain A    │ Domain B│ Domain C│
│ (overload)  │(normal) │(normal) │
└─────────────────────────────────┘
       ↓
Worker pool exhausted by Domain A
       ↓
Domains B and C latency spikes
       ↓
Customer impact across all tenants ❌
```

### Why This Matters

- **Multi-tenant SaaS**: One customer's runaway workflow shouldn't impact others
- **Internal multi-domain**: Different business units sharing infrastructure need isolation
- **Gradual workload growth**: A domain that works fine at 100 msgs/sec may break at 10,000
- **Cost efficiency**: Sharing one instance is cheaper than separate instances

### Escape Hatch (Today)

Run separate `dimd` instances per domain → ✅ isolation, ❌ cost/operational overhead. M3.4 is about having both.

## 2. Resource Accounting Model

### 2.1 Core Dimensions

We track and limit three resource dimensions per tenant:

| Dimension | Unit | Default Quota | Why |
|-----------|------|---|---|
| **Message Rate** | msg/sec | Unbounded | Inbound throughput; protects message queue |
| **Worker Slots** | count | Unbounded | Execution concurrency; protects worker pool |
| **Lineage Storage** | records | Unbounded | Lineage DB rows; protects query performance |

### 2.2 Domain Label (Already Exists)

The `domain:` label is already present in the reference architecture (data-mesh-feasibility-analysis.md §4) but not enforced. Routes can specify:

```yaml
routes:
  order-processing:
    domain: acme-corp    # Tenant identifier
    steps: [...]

  shipment-tracking:
    domain: acme-corp    # Same tenant
    steps: [...]

  vendor-onboarding:
    domain: partners     # Different tenant
    steps: [...]
```

**Scope of this design:** Route all per-tenant accounting using the `domain:` label.

### 2.3 Quota Model

Each domain gets a **quota** (a target limit) and a **current usage** (actual consumption).

```
Domain Quota:
┌─────────────────────────────────┐
│ domain: acme-corp               │
│ message_rate_limit: 1000 msg/s  │
│ worker_slots_limit: 50          │
│ lineage_quota_records: 1000000  │
└─────────────────────────────────┘

Current Usage (monitored):
┌─────────────────────────────────┐
│ message_rate: 750 msg/s (75%)   │
│ worker_slots: 40 (80%)          │
│ lineage_records: 925000 (92.5%) │
└─────────────────────────────────┘
```

When usage approaches or exceeds quota → enforce limits.

## 3. Three Resource Dimensions

### 3.1 Message Rate Limiting

**What it limits:** Inbound message throughput per domain

**Why:** Prevents a single domain from flooding the message queue and causing backlog for others.

**Implementation approach:**
- Track messages ingested per domain per time window (e.g., 1-second buckets)
- When domain exceeds rate limit: reject new messages with HTTP 429 (Too Many Requests)
- Optional: queue excess with backoff instead of rejecting

**Configuration:**
```yaml
tenants:
  acme-corp:
    message_rate_limit: 1000        # msg/sec
    rate_limit_strategy: reject     # or "queue"
```

**Tradeoff:**
- ✅ Simple, predictable enforcement
- ❌ Rejects legitimate traffic if quota too low
- ⚠️  Requires operators to set reasonable quotas

**Observability:**
```
Counter: dim_messages_rejected_total{domain="acme-corp", reason="rate_limit"}
Gauge:   dim_message_rate_current{domain="acme-corp"}
Gauge:   dim_message_rate_limit{domain="acme-corp"}
```

### 3.2 Worker Pool Partitioning

**What it limits:** Concurrent message processing per domain

**Why:** Prevents one domain's slow steps from monopolizing worker threads and blocking others.

**Implementation approach:**
- Partition worker pool by domain (static allocation per domain)
- Each domain gets a fixed number of worker goroutines
- Messages for a domain only run on that domain's workers
- If domain workers are busy: queue message, wait for a slot to open

**Configuration:**
```yaml
tenants:
  acme-corp:
    worker_slots: 50                # Concurrent messages for this domain
  partners:
    worker_slots: 20                # Fewer resources for lower-priority domain
```

**Total workers:** Sum of all domain slots ≤ instance capacity (prevent oversubscription)

**Tradeoff:**
- ✅ Hard guarantee: one domain cannot starve another
- ❌ Wastes capacity if some domains are idle
- ⚠️ Requires upfront planning of domain workloads

**Observability:**
```
Gauge: dim_worker_slots_allocated{domain="acme-corp"}
Gauge: dim_worker_slots_used{domain="acme-corp"}
Gauge: dim_worker_queue_length{domain="acme-corp"}
Gauge: dim_worker_queue_wait_seconds{domain="acme-corp"}
```

### 3.3 Lineage Storage Quota

**What it limits:** Number of lineage records per domain

**Why:** Prevents a runaway domain from filling up the lineage store, slowing queries for all domains.

**Implementation approach:**
- Track lineage record count per domain
- When domain reaches quota: reject new records with error
- Optional: expire old records (FIFO cleanup) instead of rejecting

**Configuration:**
```yaml
tenants:
  acme-corp:
    lineage_quota_records: 1000000      # 1M records max
    lineage_quota_strategy: reject      # or "expire_oldest"
    lineage_quota_retention_days: 30    # If expire_oldest: drop records > 30 days
```

**Tradeoff:**
- ✅ Predictable storage footprint per domain
- ❌ Requires periodic cleanup or record rejection
- ⚠️ Operators must balance retention vs. quota

**Observability:**
```
Gauge:   dim_lineage_records_total{domain="acme-corp"}
Gauge:   dim_lineage_quota_records{domain="acme-corp"}
Counter: dim_lineage_records_rejected_total{domain="acme-corp", reason="quota_exceeded"}
```

## 4. Configuration & Deployment

### 4.1 Quota Definition

Quotas are defined in a configuration file (YAML or JSON):

```yaml
# config/tenants.yaml
tenants:
  # Tier 1: Premium customer (high resource allocation)
  acme-corp:
    description: "ACME Corp - Premium SLA"
    message_rate_limit: 5000            # 5k msg/sec
    message_rate_strategy: queue        # Queue excess instead of reject
    worker_slots: 100                   # 100 concurrent messages
    lineage_quota_records: 5000000      # 5M records
    lineage_quota_strategy: expire_oldest
    lineage_quota_retention_days: 90
    priority: high                      # For future prioritization

  # Tier 2: Standard customer
  partners:
    description: "Partner integrations"
    message_rate_limit: 1000            # 1k msg/sec
    message_rate_strategy: reject
    worker_slots: 30
    lineage_quota_records: 500000       # 500k records
    lineage_quota_strategy: reject
    priority: normal

  # Tier 3: Low-volume
  staging:
    description: "Staging/testing"
    message_rate_limit: 100             # 100 msg/sec
    message_rate_strategy: reject
    worker_slots: 10
    lineage_quota_records: 50000        # 50k records
    lineage_quota_strategy: reject
    priority: low

# Default for unmapped domains (if not in tenants list)
default_tenant:
  message_rate_limit: 100               # Conservative default
  worker_slots: 5
  lineage_quota_records: 10000
  priority: low
```

### 4.2 Route Configuration

Routes specify which domain they belong to:

```yaml
routes:
  order-processing:
    domain: acme-corp                   # Maps to tenant config
    steps: [...]

  vendor-onboarding:
    domain: partners
    steps: [...]

  experimental:
    domain: staging
    steps: [...]
```

**If no domain is specified:** Use `default_tenant` quota.

### 4.3 Deployment Workflow

1. **Operator defines quotas** based on SLA/tier
2. **Routes reference domain** in config
3. **dimd loads tenant config** at startup
4. **Enforcement kicks in** automatically
5. **Observability shows usage** vs. quotas

## 5. Enforcement Mechanisms

### 5.1 Message Rate Enforcement

At message ingestion (adapter layer):

```
Message arrives → Get domain from route context → Check rate limit
  ├─ Within limit → Process normally
  ├─ Exceeded (reject strategy) → Return HTTP 429 + error
  └─ Exceeded (queue strategy) → Queue message, wait for next slot
```

**Where enforced:** `internal/adapters/` (HTTP, Kafka, AMQP, etc.) at message intake point.

### 5.2 Worker Slot Enforcement

At message dispatch to workers:

```
Message ready to execute → Get domain from context → Check worker quota
  ├─ Slot available → Dispatch to domain worker
  ├─ No slot (all busy) → Queue in domain-specific queue
  └─ Queue full → Apply backpressure (propagate to source adapter)
```

**Where enforced:** `internal/engine/` (GenerationManager and Executor).

### 5.3 Lineage Storage Enforcement

At lineage write time:

```
Lineage record to write → Get domain from message → Check quota
  ├─ Under quota → Write record
  ├─ At quota (reject strategy) → Log error, skip write
  └─ At quota (expire_oldest strategy) → Delete oldest record for domain, then write
```

**Where enforced:** `internal/lineage/` (Store).

## 6. Observability & Monitoring

### 6.1 Metrics

Key metrics for operators:

```
# Per-domain message rate
dim_message_rate_current{domain="acme-corp"}        # Current msgs/sec
dim_message_rate_limit{domain="acme-corp"}         # Configured limit
dim_messages_rejected_total{domain="acme-corp"}    # Total rejections
dim_message_rate_utilization{domain="acme-corp"}   # % of quota used

# Per-domain worker capacity
dim_worker_slots_allocated{domain="acme-corp"}     # Configured slots
dim_worker_slots_used{domain="acme-corp"}          # Currently in use
dim_worker_queue_length{domain="acme-corp"}        # Messages waiting
dim_worker_queue_wait_seconds{domain="acme-corp"}  # Avg wait time

# Per-domain lineage
dim_lineage_records_total{domain="acme-corp"}      # Records for domain
dim_lineage_quota_records{domain="acme-corp"}      # Configured quota
dim_lineage_quota_utilization{domain="acme-corp"}  # % of quota
dim_lineage_records_rejected{domain="acme-corp"}   # Rejected writes
```

### 6.2 Alerting Examples

```yaml
# Alert when domain uses > 80% of message rate quota
alert: DomainMessageRateHigh
expr: dim_message_rate_utilization > 0.8
duration: 5m
action: notify_operator

# Alert when domain worker queue > 100
alert: DomainWorkerQueueBacklog
expr: dim_worker_queue_length > 100
duration: 5m
action: notify_operator

# Alert when lineage reaches 90% of quota
alert: DomainLineageNearQuota
expr: dim_lineage_quota_utilization > 0.9
duration: 5m
action: notify_operator
```

### 6.3 Dashboard Example

A per-domain dashboard showing:
- Message rate (current vs. limit)
- Worker slot usage (allocated, used, queued)
- Lineage storage (records, quota, trend)
- Errors/rejections by type
- Latency distribution (should show tenant isolation working)

## 7. Design Tradeoffs

| Decision | Choice | Rationale | Tradeoff |
|----------|--------|-----------|----------|
| **Partition strategy** | Worker slots (static) | Simplicity, hard isolation guarantee | Capacity waste if uneven load |
| **Message rate strategy** | Configurable (reject/queue) | Flexibility for different SLAs | Requires operator tuning |
| **Lineage quota strategy** | Configurable (reject/expire) | Choice for data retention preference | Either lose data or reject writes |
| **Quota unit** | Per-domain (not per-route) | Simpler config, matches SLA tiers | Less fine-grained control |
| **Label source** | Use existing `domain:` label | No schema changes needed | Requires all routes labeled |
| **Enforcement layer** | Distributed (ingestion, engine, lineage) | Isolation at source | Coordination complexity |
| **Quota binding** | Static at startup | Simple, predictable | No dynamic scaling; requires restart to adjust |

---

## 8. Comparison with Alternatives

| Approach | Pros | Cons | Verdict |
|----------|------|------|---------|
| **This design** (static slots + rate limit + lineage quota) | Simple, predictable, observable | Capacity waste, requires tuning | ✅ Chosen: best balance |
| **Kubernetes-style resource requests/limits** | Flexible, dynamic | Overkill complexity for single instance | ❌ Too much overhead |
| **Time-slicing worker threads** | Better capacity utilization | Complex scheduling, hard to predict | ❌ Unpredictable latency |
| **Shared pool with weighted priority** | Fairness without wasting slots | Hard to guarantee SLA | ❌ Insufficient isolation |
| **Separate instances per domain** | Perfect isolation | High operational cost, resource waste | ❌ Defeats the purpose |

## 9. Failure Modes & Resilience

### 9.1 Configuration Missing

If a route's `domain:` label is missing or doesn't match any tenant config:
- Use `default_tenant` quota (conservative)
- Log warning so operator notices
- Exit criteria test will verify this behavior

### 9.2 Quota Exhaustion

If a domain hits quota:
- **Message rate**: Return 429; source adapter sees backpressure
- **Worker slots**: Queue in domain queue; latency increases but no failure
- **Lineage quota**: Skip write or expire old record (depends on strategy); observable via metrics

### 9.3 Quota Too Conservative

If quota is set too low and domain gets rejected:
- Operator sees high rejection rate in metrics
- Operator increases quota via config reload
- No restart required (config hot-reloadable)

### 9.4 Quota Too Liberal

If quota is set too high and domain starves others:
- Observability shows other domains degrading
- Operator decreases quota and reloads
- Gradual enforcement prevents shock

## 10. Observability-Driven Design

The design prioritizes observability so operators can:

1. **Detect imbalance**: See which domain is consuming most resources
2. **Right-size quotas**: Adjust based on actual usage patterns
3. **Verify isolation**: Confirm that overload of one domain doesn't degrade others
4. **Diagnose issues**: Trace whether a slowdown is due to quota exhaustion or other causes

**Exit criteria for M3.4.3 (tests & examples):** Run two domains with one deliberately overloaded, verify metrics show isolation working.

## 13. Future Enhancements (Out of Scope)

- **Dynamic quota adjustment**: Learn workload patterns and adjust quotas automatically
- **Spot quotas**: Allow bursting above quota during off-peak hours
- **Cross-instance coordination**: Share quota information across cluster (requires M3.1)
- **Cost metering**: Charge tenants based on resource consumption
- **Quality of Service (QoS)**: Priority-based scheduling within worker slots
- **Namespace isolation**: Separate lineage stores per domain (requires new architecture)

## Summary

M3.4.1 establishes a practical, observable resource accounting model for sharing a single `dimd` instance among multiple domains/tenants. Three resource dimensions (message rate, worker slots, lineage quota) are tracked and limited per domain, keyed on the `domain:` label already present in the reference architecture.

The design prioritizes operator observability and control: quota exhaustion is visible in metrics, and operators can adjust quotas via configuration reload without restarting.

**Status: Design complete. Ready for M3.4.2 implementation.** 🚀

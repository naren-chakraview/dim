# Phase 1 (M0.2) — Reliability & Concurrency Planning

**Status:** Planning in progress (September 1, 2026)  
**Target:** M0.2 Walking Skeleton with worker pools, retry logic, and additional step types  
**Estimated Duration:** 40-50 hours total effort  
**Tests Target:** 200+ tests passing

---

## M0.2 Vision

Build on Phase 0's foundation to add:
- **Concurrency**: Multiple workers per route (fan-out processing)
- **Reliability**: Retry with exponential backoff, classification of error types
- **Additional Steps**: Route, wiretap, idempotent, authorize
- **Multi-Route**: Single config file with multiple independent pipelines
- **Testing**: Fixture test runner for YAML-defined scenarios
- **Ordering**: Message ordering guarantees for ordered sources
- **Observability**: Prometheus metrics, OpenTelemetry tracing

---

## Critical Path Analysis

### Tier 1: Foundation (Blocking M0.2.3+)
Must complete before other work can proceed:
- **M0.2.1: Worker Pools** (4-6 hrs)
  - Extends Executor with configurable worker count
  - Thread-safe work queue, goroutine pool lifecycle
  - Backpressure & fan-out semantics
  - Impact: Unblocks retry logic, all later steps

### Tier 2: Reliability (Can run in parallel with Tier 1)
- **M0.2.2: Retry Logic** (3-4 hrs)
  - Exponential backoff with jitter
  - Transient vs. permanent error classification
  - Max attempts, max duration, circuit breaker
  - Depends: Worker pools preferred but can use M0.1 executor
  
### Tier 3a: Step Types (Can run after M0.2.1)
- **M0.2.3: Route Step** (2-3 hrs) — content-based routing with cases/default
- **M0.2.4: Wiretap Step** (1-2 hrs) — copy to secondary sink
- **M0.2.5: Idempotent Step** (2-3 hrs) — deduplication via key expression
- **M0.2.6: Authorize Step** (3-4 hrs) — RBAC/ABAC enforcement (requires principal propagation)
- Depends: Step factory pattern (M0.1), new steps are orthogonal

### Tier 3b: Multi-Route (Can run after M0.2.1)
- **M0.2.7: Multi-Route Support** (4-5 hrs)
  - Config loader: parse multiple routes from single YAML
  - Factory: instantiate multiple executors
  - CLI: `midctl run` orchestrates all routes
  - Depends: Worker pools (M0.2.1) for efficient resource sharing

### Tier 4: Testing & Observability (Can run in parallel)
- **M0.2.8: Fixture Test Runner** (2-3 hrs) — `midctl test examples/`
- **M0.2.9: Message Ordering** (4-6 hrs) — in-order delivery for ordered sources
- **M0.2.10: Observability** (2-3 hrs) — Prometheus metrics, OTel tracing
- Depends: Most tier 3 work

## Subtask Breakdown

### M0.2.1: Worker Pools (🔴 HIGH PRIORITY)
**Purpose:** Enable concurrent message processing  
**Complexity:** HIGH (4-6 hrs)  
**Depends:** Message, Channel, Executor (M0.1)

**Deliverables:**
- Executor: Add `NumWorkers` config field
- Work queue: Unbuffered channel distributing messages to workers
- Goroutine pool: Spawn/reap workers as needed
- Lifecycle: Graceful shutdown waits for in-flight messages
- Tests: 8+ tests (concurrent sends, worker exhaustion, backpressure)

**Exit Criteria:**
- ✅ Multiple workers process messages concurrently
- ✅ Backpressure still enforced via input channel
- ✅ Graceful shutdown waits for all workers to finish
- ✅ Worker count configurable (default 4)
- ✅ No race conditions with `-race` flag
- ✅ 8+ tests passing

**Risk:** Goroutine lifecycle complexity; `-race` tests must pass

---

### M0.2.2: Retry Logic
**Purpose:** Handle transient failures with exponential backoff  
**Complexity:** MEDIUM (3-4 hrs)  
**Depends:** DeadLetterEnvelope (M0.1), Config (M0.1)

**Deliverables:**
- RetryPolicy: MaxAttempts, BackoffMs, JitterMs
- Executor: Wrap step.Execute() with retry loop
- Error classification: Transient vs. permanent
- Backoff: Exponential with jitter
- Tests: 6+ tests (retry success, max exhausted, permanent error)

**Exit Criteria:**
- ✅ Failed steps retry up to MaxAttempts
- ✅ Backoff is exponential with configurable jitter
- ✅ Permanent errors skip retry, go to DLQ immediately
- ✅ Transient errors retry with backoff
- ✅ Config loading validates retry policy
- ✅ 6+ tests passing

**Risk:** Error classification requires domain knowledge; unclear which errors are transient

---

### M0.2.3: Route Step (Content-Based Router)
**Purpose:** Branch messages to different sinks based on content  
**Complexity:** MEDIUM (2-3 hrs)  
**Depends:** Step interface (M0.1), JSONata (M0.1)

**Deliverables:**
- RouteStep: Evaluates expression to determine case/default
- Config: Cases map, default target
- Multi-sink: Route implementation sends to different sinks
- Tests: 5+ tests (case match, default, missing case, error)

**Exit Criteria:**
- ✅ Expression evaluates to string (case name or default)
- ✅ Message routed to corresponding sink
- ✅ Missing case falls back to default
- ✅ No default → error to DLQ
- ✅ 5+ tests passing

**Risk:** Multi-sink output semantics (atomic vs. best-effort)

---

### M0.2.4: Wiretap Step
**Purpose:** Copy message to secondary sink without altering main flow  
**Complexity:** LOW (1-2 hrs)  
**Depends:** Sink adapter (M0.1), Step interface (M0.1)

**Deliverables:**
- WiretapStep: Sends copy to named sink, passes original downstream
- Config: Tap sink name
- Tests: 3+ tests (copy sent, original passes, tap error handling)

**Exit Criteria:**
- ✅ Message copied to tap sink
- ✅ Original message continues downstream
- ✅ Tap failure doesn't block main flow
- ✅ 3+ tests passing

**Risk:** Concurrent writes to same sink (handled by file sink append mode already)

---

### M0.2.5: Idempotent Step
**Purpose:** Suppress duplicate messages using deduplication key  
**Complexity:** MEDIUM (2-3 hrs)  
**Depends:** Step interface (M0.1), JSONata (M0.1)

**Deliverables:**
- IdempotentStep: Evaluates key expression, maintains in-memory dedup set
- Config: key_expr (JSONata expression extracting unique key)
- Dedup set: Simple map with TTL eviction (configurable, default 1 hour)
- Tests: 4+ tests (duplicate detected, unique pass, TTL expiry)

**Exit Criteria:**
- ✅ Duplicate keys are dropped
- ✅ Unique keys pass through
- ✅ In-memory set with TTL eviction
- ✅ Large dedup sets don't cause memory bloat (bounded or warned)
- ✅ 4+ tests passing

**Risk:** Memory management of dedup set for high-cardinality keys; Phase 0.2 uses in-memory only (distributed dedup in M0.3+)

---

### M0.2.6: Authorize Step
**Purpose:** Enforce RBAC/ABAC policies  
**Complexity:** HIGH (3-4 hrs)  
**Depends:** Principal propagation (M0.1 message metadata), Config (M0.1)

**Deliverables:**
- AuthorizeStep: Checks principal against roles/attributes
- Config: mode (rbac/abac), rules (JSONata for ABAC)
- RBAC: Check `principal.roles` against `require_roles`
- ABAC: Evaluate JSONata predicate with principal in scope
- Tests: 5+ tests (role match, role fail, ABAC pass/fail)

**Exit Criteria:**
- ✅ RBAC checks principal roles against require_roles
- ✅ ABAC evaluates JSONata predicate
- ✅ Denied → error to DLQ with auth error classification
- ✅ Allowed → pass through
- ✅ 5+ tests passing

**Risk:** Principal availability (requires HTTP source to extract from headers in M0.2)

---

### M0.2.7: Multi-Route Support
**Purpose:** Run multiple independent pipelines from single config  
**Complexity:** HIGH (4-5 hrs)  
**Depends:** Worker pools (M0.2.1), Config loader (M0.1), Factory (M0.1)

**Deliverables:**
- Config loader: Parse `routes: {route1: {...}, route2: {...}}`
- Factory: BuildPipeline extended to handle multiple routes
- Executor manager: Start/stop all routes together
- Shared resources: HTTP source listening for all routes
- Tests: 4+ tests (dual routes, independent execution, shutdown)

**Exit Criteria:**
- ✅ Config can define multiple routes
- ✅ Each route has independent executor, steps, sinks
- ✅ HTTP source accepts messages for any route
- ✅ Routes process concurrently without interference
- ✅ Shutdown is coordinated (all routes stop together)
- ✅ 4+ tests passing

**Risk:** Resource contention (multiple executors on single system); shared HTTP source

---

### M0.2.8: Fixture Test Runner
**Purpose:** Test routes using YAML-defined input→output pairs  
**Complexity:** MEDIUM (2-3 hrs)  
**Depends:** Config loader (M0.1), Executor (M0.1), Test harness

**Deliverables:**
- Test loader: Parse `test/fixtures/*.yaml` with input/expected_output/expected_error
- Test runner: Send input through pipeline, capture output
- Assertion: Compare actual vs. expected (with JSONata path matching)
- `midctl test`: CLI command runs all fixtures
- Tests: Integration tests (successful fixture, expected error, mismatch detected)

**Exit Criteria:**
- ✅ `midctl test examples/` runs all fixtures
- ✅ Input sent through pipeline
- ✅ Output compared to expected (exact match or JSONata path)
- ✅ Error cases tested (filter rejection, step failure)
- ✅ Test report shows pass/fail/error
- ✅ Integration tests passing

**Risk:** Fixture format design (too strict → brittle, too loose → doesn't catch bugs)

---

### M0.2.9: Message Ordering Guarantees
**Purpose:** Guarantee in-order delivery for ordered sources  
**Complexity:** HIGH (4-6 hrs)  
**Depends:** Worker pools (M0.2.1), Message metadata (M0.1)

**Deliverables:**
- Metadata: Add `sequence_number` to message
- Config: Mark sources/routes as ordered/unordered
- Executor: Single-worker mode for ordered routes (or ordered queue + workers)
- Tests: 6+ tests (ordering maintained, concurrent workers, ordering violation detected)

**Exit Criteria:**
- ✅ Messages tagged with sequence number
- ✅ Ordered routes preserve FIFO order
- ✅ Unordered routes allow worker parallelism
- ✅ No out-of-order processing for ordered routes
- ✅ 6+ tests passing

**Risk:** Performance trade-off; ordered routes can't use worker pools (sequential only)

---

### M0.2.10: Observability (Metrics + Tracing)
**Purpose:** Add Prometheus metrics and OpenTelemetry tracing  
**Complexity:** MEDIUM (2-3 hrs)  
**Depends:** Executor (M0.1), Adapters (M0.1)

**Deliverables:**
- Metrics: Messages in/out, step latencies, errors, retry attempts
- Prometheus: Expose `/metrics` endpoint
- OTel: Span per message, span per step, trace propagation
- CLI: `midctl trace tail` (mock/simple for Phase 0)
- Tests: Integration tests (metrics emitted, traces recorded)

**Exit Criteria:**
- ✅ Prometheus metrics exported on `/metrics` endpoint
- ✅ OTel tracer configured and spans recorded
- ✅ Key metrics: throughput, latency, error rate
- ✅ Spans include step name, duration, status
- ✅ Integration tests passing

**Risk:** OTel SDK integration; per-message overhead
